## 二、为什么用结构体定义寄存器（而不是一堆宏）

### 结构体版

```c
typedef struct
{
    volatile uint32_t CRL;    /* 0x00 */
    volatile uint32_t CRH;    /* 0x04 */
    volatile uint32_t IDR;    /* 0x08 */
    volatile uint32_t ODR;    /* 0x0C */
    volatile uint32_t BSRR;   /* 0x10 */
    volatile uint32_t BRR;    /* 0x14 */
    volatile uint32_t LCKR;   /* 0x18 */
} GPIO_TypeDef;

#define GPIOA  ((GPIO_TypeDef *)0x40010800UL)
#define GPIOB  ((GPIO_TypeDef *)0x40010C00UL)
```

### 两种写法对比

| 对比项 | 宏写法 | **结构体写法** |
|---|---|---|
| 定义量 | 7 寄存器 × 5 端口 = **35 个宏** | **1 个结构体 + 5 个指针** |
| 访问 | `GPIOB_BSRR = x` | `GPIOB->BSRR = x` |
| **能不能把端口当参数传** | ❌ **不能**（宏不是变量） | ✅ **能**：`gpio_set(GPIOB, 13)` |

**第 3 条是决定性的** —— 宏写法**写不出通用函数**，必须每个端口复制一遍代码。

### 结构体指针是怎么对应到寄存器的

```
GPIOA->ODR
= (*(GPIO_TypeDef *)0x40010800UL).ODR          ← 语法糖展开
= *(volatile uint32_t *)(0x40010800 + 0x0C)    ← ODR 偏移 0x0C
= *(volatile uint32_t *)0x4001080C             ← 最终
```

**结构体的作用就是"让编译器替你算偏移"** —— 本质和手写宏完全一样，只是更好读、能传参。

### 为什么 `volatile` 必须写在**成员**上

```c
typedef struct { volatile uint32_t ODR; ... } GPIO_TypeDef;
                          ↑ 加在类型上
```

因为 `GPIOA` 是 `GPIO_TypeDef *` 指针。`volatile` 加在**成员类型**上，才能保证 `GPIOA->ODR` 的**每次访问都是真实读写**（不缓存到 CPU 寄存器、不被优化掉）。

### 结构体大小必须是 0x1C

7 × 4 字节 = **28 字节 = 0x1C**。所有成员都是 `uint32_t`（4 字节对齐），ARM 上**不会有填充**，所以偏移正好对上寄存器地址。

> 可加编译期检查防止以后加成员忘了算：
> `typedef char chk[(sizeof(GPIO_TypeDef) == 0x1C) ? 1 : -1];`

## 三、CRL / CRH：引脚配置（最容易错的地方）

### 结构

```
每个引脚占 4 位：  [CNF1 CNF0 MODE1 MODE0]
                    └── 高2位 ──┘ └─ 低2位 ─┘

CRL 管 P0~P7      CRH 管 P8~P15
```

### 位位置的计算规则

| 引脚范围 | 用哪个寄存器 | 位位置 |
|---|---|---|
| `pin < 8` | **CRL** | `pin × 4` |
| `pin >= 8` | **CRH** | `(pin - 8) × 4` |

### ⚠️ 关键理解：位位置只取决于"组内序号"

| 引脚 | 寄存器 | 位位置 | 说明 |
|---|---|---|---|
| PB5 | GPIOB->**CRL** | `5 × 4 = 20` | 组内第 5 个 |
| PC13 | GPIOC->**CRH** | `(13-8) × 4 = 20` | 组内也是第 5 个 |

**两者位位置都是 20 —— 不是巧合，是必然**，因为都是"组内第 5 个引脚"。

**但寄存器完全不同**：
```
GPIOB->CRL = 0x40010C00 + 0x00 = 0x40010C00
GPIOC->CRH = 0x40011000 + 0x04 = 0x40011004
```

**这就是为什么 `gpio_config` 必须按 `pin < 8` 分支。**

### 常用配置值（4 位字段的整体值）

| 模式 | CNF | MODE | 值 | 用途 |
|---|---|---|---|---|
| 推挽输出 50MHz | 00 | 11 | **0x3** | **点 LED** |
| 开漏输出 50MHz | 01 | 11 | **0x7** | I2C |
| 复用推挽 50MHz | 10 | 11 | **0xB** | USART TX / SPI |
| 复用开漏 50MHz | 11 | 11 | **0xF** | I2C 复用 |
| 模拟输入 | 00 | 00 | **0x0** | ADC |
| 浮空输入 | 01 | 00 | **0x4** | 串口 RX |
| 上拉/下拉输入 | 10 | 00 | **0x8** | 按键 |

## 四、BSRR：原子置位/复位（比 ODR 安全）

### 位定义

| 位范围 | 作用 |
|---|---|
| **bit0~15** | **置位**（写 1 有效，写 0 无影响） |
| **bit16~31** | **复位**（写 1 有效，写 0 无影响） |

```c
port->BSRR = (1UL << pin);          /* 置位：输出高 */
port->BSRR = (1UL << (pin + 16));   /* 复位：输出低 */
```

### 为什么不用 `ODR |= / &= ~`

| 写法 | 本质 | 问题 |
|---|---|---|
| `port->ODR \|= (1<<pin)` | **读-改-写**（读 ODR → 改 → 写回，3 步） | **中断场景有竞态**：读完之后被中断，中断改了别的位，写回时把中断的改动覆盖掉 |
| `port->BSRR = (1<<pin)` | **单次写，原子操作** | ✅ 无竞态 |

**结论：中断里改 GPIO 必须用 `BSRR`。主循环里用 ODR 也能跑，但 BSRR 更安全、更统一。**

## 五、工程实践要点

### 1. 为什么把 GPIO 操作写成 `static inline`

| 方式 | 开销 | 缺点 |
|---|---|---|
| 普通函数（.c 里） | 压栈/跳转/返回，**几 us** | 中断里开销明显 |
| **`static inline`** | **编译时展开，零开销** | 代码体积略大 |
| 宏 | 零开销 | **无类型检查**、调试看不到 |

**`static inline` 是 GPIO 操作的标准做法。**

### 2. 顺序：先配模式，再写数据

```c
/* 推荐 */
gpio_config(GPIOA, 12, GPIO_CFG_OUT_PP_50MHZ);   /* ① 先配模式 */
gpio_set(GPIOA, 12);                              /* ② 再写数据 */

/* 也能跑，但会有毛刺 */
gpio_set(GPIOA, 12);
gpio_config(GPIOA, 12, GPIO_CFG_OUT_PP_50MHZ);
```

**原因**：配置成输出的瞬间，引脚会立刻驱动 `ODR` 的**当前值**（默认 0）。先写 ODR 就不会出现"配置完先输出一个低电平毛刺"。


### 3. `gpio_config` 里的防呆

```c
port->CRL |= ((cfg & 0xFUL) << (pin * 4));   /* 加 & 0xFUL 掩码 */
```

如果传了超过 4 位的错误值（如 `0x13`），不加掩码会**溢出并污染相邻引脚**。
